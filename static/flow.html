The big picture

You ask a question. Four agents take turns working on one shared piece of state until a reviewed answer exists. They never call each other: a supervisor reads the state and decides who goes next.

Remember

Load your preferences and related past facts from SQLite into the state.

Research

The model drives a tool loop: it decides what to search and which pages to read, then writes cited findings.

Review

Code checks the citations, then a model checks the claims. Rejected? One more research round.

Answer

The finalizer turns approved findings into the answer you read.

Save

If the answer was approved, a short summary is stored for next time.

The graph

Built in graph.py with LangGraph's StateGraph. Every worker hands control back to the supervisor (hub-and-spoke), so all routing lives in one function. Click any node to see what it does.

── fixed edge (always taken)- - conditional edge (supervisor decides)

Four words that are easy to mix up

Node — a Python function state → partial update registered in the graph. The unit LangGraph executes. e.g. agents.researcher
Agent — a node with a role that makes a decision, by calling a model (researcher, reviewer, finalizer) or by rules (supervisor). load_memory is a node but not an agent.
Edge — a transition. Fixed edges always fire; the one conditional edge calls route_from_supervisor(state), which returns the name of the next node.
Tool — a plain function that touches the outside world (web_search, fetch_page). Not part of the graph. The model asks for tool calls, and the researcher's code runs them. Choosing a tool is not routing: control never leaves the researcher node.

Shared state and how updates merge

The state is a TypedDict in state.py. A node receives the whole thing but returns only the keys it changed. LangGraph merges that partial update using each key's reducer.

Replace (default)

Most keys: the new value overwrites the old. That's why the second research round replaces the first round's research_findings.

review_status: ReviewStatus
research_findings: str

# old: "pending"   update: "approved"
# new: "approved"

Append (operator.add)

history and tool_calls accumulate across nodes and retries, so nothing is lost from the trace.

history: Annotated[list[HistoryEntry], operator.add]

# old: [a, b]   update: [c]
# new: [a, b, c]
Why the researcher never calls the reviewer: it sets review_status="pending" and returns. The supervisor sees "pending" and routes to the reviewer, which reads research_findings from state. Agents are decoupled; you can swap, test or reorder them without touching each other.

Neither is "better" by default. That is what an evaluation set is for: run both on the same questions and compare quality and cost.

Tool call flow, step by step

Every call made during one agentic research round, in order: to the model, to the tools, and to the internet. Solid arrows are calls, dashed arrows are return values. Pick a scenario, then step through it (or click any arrow).

Rules every tool follows
  • Never raises. Network errors, timeouts, 403s, PDFs and empty results all become a record with ok: false and an error message.
  • Always recorded. Every call is appended to state.tool_calls, success or failure.
  • Provider is visible. ddgs, http or mock, so a mock result is never mistaken for a real one.
  • Failures go back to the model. A failed search or fetch becomes a tool result such as "web_search failed: …", so the model can retry differently. Only if the round ends with no sources at all does the run stop with an error.
  • Bounded. 5 results per search, at most 3 searches and 4 page reads per round, 10 s timeout and 2 MB cap per page, 3,000 chars kept per page. All but the timeout and cap are set in .env.
  • The model asks, code executes. The model only produces a request ({"name": "fetch_page", "arguments": "{\"source_id\": 2}"}). Validation, budgets, the network call and error handling all happen in Python.

What the LLM actually sees

Each model call is stateless. The model cannot read the graph state; it sees only the text a node copies into the prompt. Deciding what goes in (and what stays out) is the engineer's job.

The supervisor makes no model call: its routing is plain Python rules in decide_next_step(). Only the researcher gets tools; the reviewer and finalizer read web text but have no way to act, which limits what a prompt injection could do. In the inspector, open the LLM tab on any step to see the exact messages, and the HTTP lab shows the same requests at the raw HTTP level.

Retry limit and failure paths

All of these are decided by decide_next_step() in agents.py, checked in this order:

Condition in stateNext nodeWhy
final_answer is setsave_memoryWork is done; persist and finish.
error is setfinalizerSearch or model failed. The finalizer writes "I could not produce a reliable answer" without calling the model. Nothing is saved to memory.
review_status = not_startedresearcherNo research yet.
review_status = pendingreviewerNew findings need review.
review_status = approvedfinalizerGood to answer.
rejected and revision_count < MAX_REVISIONSresearcherRetry. The supervisor increments revision_count.
rejected after a revision, and review_score didn't improvefinalizerStuck detection: another revision is unlikely to help, so stop early and mark it unapproved.
rejected and limit reachedfinalizerAnswer anyway, but marked "did NOT pass review"; outcome="unapproved"; not saved to memory.

The limit lives in code, not in a prompt, so a model can never talk its way into an infinite loop. The same idea applies one level down: inside the researcher, the tool loop is capped by MAX_TOOL_TURNS, MAX_SEARCHES and MAX_FETCHES. Two nested loops, both bounded by code. As a last safety net, every run sets LangGraph's recursion_limit just above the longest legitimate path, so a routing bug fails fast.

How the inspector gets a live trace

The browser can't run Python, so server.py runs the graph and streams each step as it happens using Server-Sent Events.

BrowserEventSource("/api/run?question=…")
→
server.pywraps the model in RecordingLLM (records every complete() and chat() turn), builds the graph
→
graph.stream(debug)task event = state in; task_result = update out
→
SSE eventsnode_start, node_end (+ drained LLM calls), done
→
Pageanimates the graph, renders a card per step

The agents don't know they're being recorded: RecordingLLM has the same complete() and chat() interface as the real client. That's the payoff of injecting dependencies. The researcher's step card shows one LLM call per loop turn, each with its finish_reason and tool_choice.
